# 普通模式卡顿修复

本次针对 `normal` 模式的 TCP 转发链路排查。以下是代码中可确认的问题；实际公网卡顿是否全部由这些问题导致，还需要部署后的网络观测。

## 原因与修改

| 问题 | 触发条件与影响 | 修改 |
| --- | --- | --- |
| IO 线程同步解析 DNS、等待目标建连 | 域名解析或目标连接慢时，同一线程上的其他连接也无法及时处理 | 普通转发使用 Netty 异步 DNS / connect，TCP 建连超时 10 秒；连接前暂停来源读取，建立后按顺序发送首批数据 |
| 把 TCP 一次读取当作完整首包 | IV、IPv4 / IPv6 / 域名地址头被拆开时，抛异常或解析错误 | 分别累积 IV 和地址头，收齐后再继续；状态仅保存在当前连接中 |
| 无业务数据时未剥离地址头 | 首包只有目标地址，地址头被作为网站请求发送 | 始终剥离地址头；即使负载为空也建立连接，支持服务器先发欢迎消息的协议 |
| 活跃连接使用可过期缓存 | 超过 5 分钟没有上行应用数据，或缓存容量淘汰后，下次上行重新创建解密器 | 改为 Channel 属性保存状态，生命周期与连接一致；客户端关闭时释放目标连接 |
| 缺少双向背压 | 上传或下载某一端较慢，待发送数据持续堆积 | 依据目标写队列可写状态暂停来源读取，恢复可写后继续；复用反向隧道不启用整条隧道的逐流暂停 |
| heap ByteBuf 返回 null | 收到堆内存缓冲区时丢数据或抛异常 | 统一根据 readerIndex / readableBytes 读取 heap、direct、slice，并释放引用 |
| 收包反复复制、逐包 INFO 日志 | 大量分段和高流量增加内存分配与控制台 IO | 请求聚合改为可增长缓冲；转发逐包日志改为受开关保护的 DEBUG |
| 关闭时阻塞、重复关闭通知 | IO 回调同步等待 close，异常路径重复通知 | close 不阻塞；TCP 客户端异常仅由 inactive 事件通知关闭 |

## 验证与构建

在仓库根目录运行：

```sh
mvn -pl vpn -am test
mvn package
```

同时固定 Assembly 插件版本并将已移除的 `assembly` goal 改为 `single`，修复新 Maven 环境无法打包的问题。产物是 `vpn/target/panama.jar`。现有 `panama.config` 无需修改。

新增测试覆盖：

- 7 种现有加密算法的 IV 分段与逐字节解密。
- IPv4、IPv6、域名和最大长度域名头的所有截断位置。
- 加密请求各首包边界、仅地址头、后续多段数据及连接状态复用。
- heap / direct / slice 缓冲区读取及引用释放。
- 真实本地 TCP：域名目标、服务器先发消息、1 MiB 双向数据完整性、客户端断开释放目标、连接拒绝及时结束。
- 人为延迟 DNS 时 IO 线程继续工作，连接前写入保持顺序。
- 双向写队列不可写时暂停读取、恢复后继续传输。

验证不等同于公网吞吐基准。此次保留协议和生产依赖版本；未针对 `inner` / `outer` 做端到端回归。编译为 Java 8 API/字节码并在本机 JBR 25 运行测试，未在 Java 8 运行时实测。

异步解析依赖服务器可用的 DNS 配置。上线后建议复测原先最容易卡顿的网站、持续下载以及闲置后恢复连接，观察首字节延迟、CPU 和内存变化。

相关 API：[Netty DNS resolver](https://netty.io/4.1/api/io/netty/resolver/dns/DnsAddressResolverGroup.html)、[ChannelConfig AUTO_READ](https://netty.io/4.1/api/io/netty/channel/ChannelConfig.html)。
